第7週：從隨機、貪婪到 Beam Search（21×21 找金幣）

🎯 本週學習目標

  • 理解為什麼「隨機」與「貪婪」在大地圖中表現不佳
  • 學會選擇更適合題目條件的演算法
  • 認識並實作 Beam Search（可調整 K）
  • 用 Beam Search 在 21×21 地圖中找高分路徑（100 步）

一、題目環境（本週正式規格）

  • 地圖大小：21 × 21
  • 每格金幣：-5 ～ +5
  • 金幣只能吃一次，但可以重複進入格子
  • 最多移動 100 步
✅ 規則提醒：某格金幣只在「第一次進入」時增減；第二次起同格的金幣視為 0（不再加/扣）。
✅ 但為了教學觀察：地圖畫面永遠顯示「初始金幣數」，不會被改寫成 0。

二、第一種方法：隨機演算法（Random）

「每一步隨機選一個可以走的方向」

  • 優點：好寫、一定跑得動
  • 缺點：容易吃到負分、繞圈、浪費步數

三、第二種方法：貪婪演算法（Greedy）

「每一步選下一格金幣最多的方向」

  • 優點：比隨機好、容易理解
  • 缺點：只看眼前，容易卡在局部區域或高分陷阱
👉 隨機沒有方向；貪婪方向太短。接著我們學 Beam Search：同時保留多條路。

四、Beam Search 最適合的原因（對應本題環境）

  • 地圖大（21×21），DFS/BFS 全搜容易爆炸
  • 金幣只能吃一次 → 路徑「歷史」會影響未來分數
  • Blockly/JS 需要「跑得動、寫得出來」

Beam Search：每一步保留前 K 條有希望的路，淘汰其餘路徑，在有限資源下取得穩定高分。

💡 K（Beam Width）越大：通常越容易找到更高分，但計算量也越大。

六、Beam Search 演算法程式解析（教師講解用）

核心精神一句話：
「同時保留多條有希望的路，每一步淘汰表現不好的。」

1) 為什麼 K（Beam Width）會影響結果？

  • K 小：跑很快，但容易錯過更好的路（像只挑少數候選）
  • K 大：同時保留更多可能性，通常能找到更高分，但計算量更大
教學建議：先用 K=1 讓學生看到「幾乎變成貪婪」，再調到 K=4 或 K=8 對照分數差異。

2) 本題 path（路徑）資料結構

  • r, c：目前位置
  • coins：已取得的實際分數（只吃一次）
  • visited：Set，記錄已吃過金幣的座標
  • route：完整路徑座標序列（用於輸出與防折返）

3) 為什麼「金幣只能吃一次」要用 visited？

const key = `${nr},${nc}`; const alreadyTaken = p.visited.has(key); const gain = alreadyTaken ? 0 : baseMap[nr][nc];

第一次進入才會把 baseMap 的值加進 coins；第二次起 gain=0，不再重複加分或扣分。

4) 為什麼要「禁止立即折返」？

if (prevPrev && nr === prevPrev.r && nc === prevPrev.c){ continue; // 不允許 A->B->A 立即折返 }

避免出現 A↔B 兩格來回浪費步數的 2-cycle。

5) 評分函數 scorePath 的作用

score = coins + neighborPositiveSum - revisitPenalty
  • coins：真實分數（已吃到的金幣）
  • neighborPositiveSum：附近正金幣估計值（提供方向感）
  • revisitPenalty：重訪懲罰（避免繞圈浪費步數）

6) 每一步的 Beam 操作（保留前 K 名）

next.sort((a,b) => scorePath(b) - scorePath(a)); paths = next.slice(0, K);

每一步把所有候選路徑 next 排序後，只保留前 K 條，這就是 Beam Search 的「寬度限制」。

老師可用一句話總結：
「K 越大，同時保留的可能性越多，越不容易走錯；但也越花時間。」
